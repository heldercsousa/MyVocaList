● Looking at your log, the ANR trigger is right there in the numbers:

  PeoplePage loaded        = 8155ms  (ctor→Loaded)
  PersonsViewModel fetch   = 8444ms
  PersonsViewModel initAsync = 8523ms
  PeoplePage navigatedTo   = 9961ms

  Android throws the "isn't responding" dialog when the UI thread is 
  unresponsive for ~5 seconds. Your PeoplePage is taking 8–10s to become
  interactive, so you blow past that threshold every time you navigate to it.
  The HttpMessageHandler cleanup cycle lines are just IHttpClientFactory
  background maintenance on a 10s timer — harmless noise, not the cause.

  There are really two separate things going on, and it's worth not conflating
  them:

  1. Debug-environment slowness (the biggest multiplier)

  This log is a Debug build attached to vsdbg. MAUI Debug builds run 5–10×
  slower than Release: no XamlC, JIT instead of AOT, plus debugger
  thread-pausing overhead. A page that loads in ~1s in Release can genuinely
  take 8s under the debugger. So a large chunk of that 8155ms is not your app —
  it's the harness.

  Quick relief options (in rough order of effort):

  - Suppress the ANR dialog on the emulator so it stops interrupting you:
  adb shell settings put secure anr_show_background 0
  adb shell settings put global anr_show 0
  - (Not all API levels honor these; the reliable one is below.)
  - Extend/disable the ANR timer for your package while debugging — set your app
  as the persistent debug-app so the watchdog backs off:
  adb shell am set-debug-app -w --persistent com.myvocalist
  - Clear it later with adb shell am clear-debug-app.
  - Test in a Release/AOT build when you're not stepping through code. Most "is
  the app fast enough" testing should happen on Release anyway — Debug timings
  are not representative of what users see.

  2. Real app-load cost (the part worth fixing)

  Even accounting for Debug overhead, an 8s fetch is suspicious and it lines up
  with work you already have in flight. Your own constraints registry documents
  the root cause:

  ▎ Microsoft.Data.Sqlite executes async methods synchronously — no real async 
  ▎ I/O. Any EF Core "async" query awaited on the UI thread runs entirely ON the
  ▎ UI thread and freezes the app.

  And memory shows this is exactly the open page-load-frozen Phase 2 work —
  where the finding was "S23 freeze is UI-render cost, not DB" and the next step
  is "fix 5 Release-only XamlC errors, build Release APK for T2." So the
  performance side is already tracked, not a new discovery.

  ---
  My recommendation: for the immediate annoyance, use am set-debug-app 
  --persistent to stop the watchdog from interrupting your debug sessions, and
  do your "does it feel fast" testing on a Release build. Keep the actual
  load-time fix inside the existing page-load-frozen Phase 2 stream rather than
  reacting to Debug-build numbers.

  the orchestrator read-scope rule) to see whether the 8s is DB, render, or

  - (b) just help you get the emulator/ADB setup so the ANR dialog stops
  interrupting you?

  Which is the actual pain you want gone first — the popup, or the load time?

            Reason: Input dispatching timed out … Waited 5001ms for MotionEvent

  This is the authoritative cause: the main (UI) thread did not consume a 
  touch-up event for 5001 ms, so Android raised the ANR dialog. Everything else
  in the log is a symptom of that same stall.

  What the CPU snapshot rules out — this is the important part

  The ANR CPU dump (19:34:24) shows:

  73% system_server (kernel) — the OS busy DUMPING the ANR stacks
   4% 8316/com.myvocalist: 4% user + 0% kernel
        4% 8361/RenderThread

  Your app is using ~4% CPU during its own hang, and the main thread (8316)
  isn't even in the busy list. Combine that with:

  - some avg10=0.21 on /proc/pressure/io → not disk-I/O bound
  - iowait 1.9% → negligible

  Conclusion: the UI thread is not computing and not waiting on disk — it is 
  blocked waiting (on a lock or an await). That is the exact signature of your
  documented constraint:

  ▎ Microsoft.Data.Sqlite executes async methods synchronously — an EF Core 
  ▎ "async" query awaited on the UI thread runs entirely ON the UI thread and 
  ▎ freezes the app. (constraints-registry.md)

  So the 8155 ms PeoplePage load in the first dump and this ANR are the same 
  defect: a SQLite call (or the static DB load gate that was added to work
  around it) is being awaited on the main thread, blocking touch dispatch past 5
  s.
