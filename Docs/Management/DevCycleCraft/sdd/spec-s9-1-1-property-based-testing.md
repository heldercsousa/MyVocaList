## Overview

Property-Based Testing (PBT) is a complementary testing strategy that verifies invariants across generated inputs rather than specific example input-output pairs. In the context of Spec-Driven Development, PBT solves a critical problem: **when the same specification is implemented multiple times by the same AI agent (across sessions) or different agents, how do you verify that all implementations are equally correct?**

Traditional example-based tests (TDD's primary form) validate specific cases: `sort([3,1,2]) == [1,2,3]`. Property-based tests define universal truths: "for any list, sorting twice is idempotent" or "output length equals input length." The testing framework then generates hundreds or thousands of random inputs to verify these properties hold.

This distinction is load-bearing for AI-assisted development. Code generated by an LLM in session A may look completely different from code generated in session B, yet both are correct if they satisfy the same properties. Property-based testing captures the *what* (properties that must hold) rather than the *how* (specific implementation details or output values), making it ideal for validating spec conformance across regenerations.

## Why PBT Matters for SDD and Non-Determinism

### The Non-Determinism Problem in AI-Assisted Code

When an AI agent generates code to satisfy a specification, the implementation can vary significantly:
- Different algorithmic approaches (linear scan vs. binary search, recursive vs. iterative)
- Different variable names, organization, or optimization strategies
- Different edge case handling order (validate first vs. validate during processing)

Traditional TDD tests written against the *first* implementation may pass only on that specific implementation. If the specification is updated and code is regenerated, the new implementation might produce different intermediate behavior (different variable orders, different recursion patterns) but still be correct by the spec.

**Property-based testing decouples correctness from implementation.** It verifies that the specification's contract holds regardless of how the code is structured. This is especially critical in SDD where:

1. **Code regeneration is expected.** Specs evolve; code is regenerated from new specs. Property tests survive regeneration because they test contracts, not implementation details.
2. **Multiple correct implementations exist.** A sorting function using quicksort and one using mergesort are both correct. Example tests might pass on one and fail on the other. Property tests pass on both.
3. **LLM hallucinations hide in implementation details.** An agent might "optimize" in a way that breaks an edge case. Spot checks with example tests miss this. Property tests explore thousands of inputs and find the failure.

### PBT for LLM Code Generation

Recent research (2025-2026) demonstrates that **Property-Based Testing paired with TDD reduces AI code hallucinations by 23-37% compared to example-based TDD alone** (arXiv 2506.18315, Property-Generated Solver framework). The reason: properties capture semantic intent better than examples do.

When an agent tries to "fake" its way to passing a property test, the shrinking mechanism (automatic reduction of failing inputs to minimal counterexamples) forces the agent to implement the full algorithm. There is no shortcut. The properties are too broad, too universal.

Example from research: an agent implementing integer factorization could "fake" 10 example-based tests by hardcoding specific factorizations. But the property "product of factors equals the original integer" cannot be hardcoded and holds for all integers. The agent must implement the real algorithm.

## Property Categories and Invariants for SDD

### Round-Trip Properties

**Definition:** Encoding then decoding returns the original value.

Example: JSON serialization or data transformation round-trips.

**When to use:** APIs, serialization, data transformations, parsers. Critical for data pipeline correctness.

### Idempotence

**Definition:** Applying an operation twice produces the same result as once.

Example: Sorting a list twice produces the same result as sorting once.

**When to use:** Caching operations, normalization, string transformations, deduplication. Catches bugs where an operation is applied incorrectly when called repeatedly.

### Invariant Properties

**Definition:** A condition that holds before and after a transformation.

Example: Pagination preserves total count and prevents duplicates across pages.

**When to use:** Database queries, list operations, collection transformations. Ensures that operations preserve critical properties (length, uniqueness, ordering).

### Commutativity and Associativity

**Definition:** Order of operations doesn't matter (or matters in a predictable way).

Example: Addition and multiplication are commutative; order of queue entries should be deterministic.

**When to use:** Mathematical operations, state mutations, parallel operations. Catches ordering bugs or race conditions.

### Oracle / Differential Testing

**Definition:** Compare against a known-correct (but slower) reference implementation.

Example: Compare binary search results against linear search (trusted baseline).

**When to use:** Performance optimizations, algorithm variants, refactorings. Provides high confidence that a faster implementation is still correct.

### Content Safety and Boundary Properties

**Definition:** Output respects size, format, or safety constraints.

Example: API response never exceeds requested page size; queue never has negative participants.

**When to use:** API responses, UI constraints, security boundaries, resource limits. Catches off-by-one errors and boundary condition bugs that example tests miss.

## PBT in Combination with TDD Red-Green-Refactor

Property-based tests fit naturally into the TDD cycle:

### Phase 1: Red
The Tester writes both example-based tests AND property-based tests. Properties capture the spec's invariants; examples capture specific acceptance criteria.

### Phase 2: Green
The Builder implements code that passes both. Example tests verify specific cases; property tests verify the algorithm works across all cases.

### Phase 3: Refactor
Properties are the safety net. Refactoring is safe because properties verify the contract, not the implementation. If the refactored code still satisfies all properties, it's correct.

## When PBT Complements TDD (and When It Doesn't)

### Use PBT When:
- **Properties are clear from the spec.** "Sorting must be idempotent" is clearly a property. "The user must see a welcome message on first launch" is not.
- **The function transforms collections or performs calculations.** Sorting, filtering, pagination, parsing, serialization all have obvious properties.
- **Edge cases are hard to predict.** Properties explore thousands of inputs, finding boundaries you wouldn't write by hand.
- **Multiple implementations might be correct.** Regenerated code from updated specs should satisfy the same properties.
- **Refactoring is planned.** Properties are your safety net for optimization and restructuring.

### Stick with Example-Based Testing When:
- **Behavior is scenario-dependent.** "If the user is on Android, show X; on iOS, show Y" is not a property — it's a specific example.
- **Side effects or external state matter.** UI state, database triggers, or network calls are hard to express as properties.
- **The test's value is documentation.** Specific examples that illustrate behavior are valuable documentation.

### Recommendation for MyVocaList
Use **both** in a strategic combination:

1. **Example-based tests** for each requirement in `tasks.md` (specific acceptance criteria)
2. **Property-based tests** for collections, pagination, validation rules, and data transformations
3. **Ratio:** ~70% example-based (TDD driving incremental features), ~30% property-based (verifying invariants)

## PBT and Hallucination Prevention

Research from "Agentic Property-Based Testing" (arXiv 2510.09907) and "Property-Generated Solver" (OpenReview 2026) shows that PBT is particularly effective at catching AI hallucinations because:

1. **Shrinking forces completeness.** When a property fails, the framework shrinks the input to the minimal case. The agent cannot hardcode around it — it must implement the full algorithm.

2. **Properties are harder to fake.** An example-based test might be satisfied by a hardcoded case. A property like "for any integer, product of its factors equals the integer" cannot be hardcoded across the entire integer domain.

3. **Properties capture intent, not syntax.** An agent focusing on making examples pass may miss the intent. Properties encode intent directly: "the output must always be non-decreasing" vs. "sort([3,1,2]) returns [1,2,3]".

## Known Limitations and Mitigations

### Limitation 1: Property Definition is Hard
Writing good properties requires thinking about what must always be true. It's a different mindset than writing examples.

**Mitigation:** Start with simple properties (round-trip, idempotence, invariants). Use templates from this document. Have the Tester use the property categories above as a checklist.

### Limitation 2: Flakiness from Non-Deterministic Input Generation
Random input generation can occasionally fail to trigger a property on the first run, especially for properties with rare preconditions.

**Mitigation:** PBT frameworks provide seed control and shrinking. Use seed reproducibility to isolate failures. Accept that rare failures are discoverable — they reveal bugs other tests miss.

### Limitation 3: Complex Systems Are Hard to Property-Test
Testing a stateful system with many interacting components requires careful property design.

**Mitigation:** Use **stateful testing** with rule-based state machines (advanced feature in FsCheck/Hypothesis). Define invariants that must hold after each operation sequence.

### Limitation 4: Performance
Generating and testing thousands of inputs takes time. Large collections or expensive operations can slow CI/CD.

**Mitigation:** Balance number of examples. Configure test count in FsCheck to reduce in CI, increase locally during development. Separate fast unit properties from slow integration properties.
