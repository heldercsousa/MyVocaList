## Overview

The spec-first tooling landscape matured significantly in 2025–2026. Three tools dominate: **Amazon Kiro**, **GitHub Spec Kit**, and **Tessl**. All three operationalize SDD by structuring development around a requirements → design → tasks → implementation pipeline, but they differ materially in philosophy, scope, maturity, and adoption.

This topic covers the capabilities, positioning, and trade-offs of each tool. Vendor lock-in and tool-switching friction are addressed in S7.1.1 and S7.1.2 respectively.

---

## Amazon Kiro

**Release:** July 2025 (GA)  
**Model:** Proprietary IDE + CLI  
**Repository:** https://github.com/kirodotdev/Kiro (3,353 stars as of March 2026)

Kiro is an agentic IDE — a fork of VS Code built specifically for spec-driven development. It takes natural language prompts and produces structured spec artifacts (requirements, design, tasks) that drive code generation.

### Core Architecture

Kiro operates on a three-phase workflow:

1. **Requirements & Design Phase** – Kiro converts a natural language prompt into:
   - `requirements.md` — User stories with acceptance criteria in EARS notation
   - `design.md` — Technical design document with data flow diagrams, TypeScript interfaces, database schemas, API endpoints
   - Design clarity is generated by analyzing the approved spec and codebase

2. **Task Decomposition** – Kiro generates `tasks.md`:
   - Discrete, sequenced implementation tasks
   - Dependencies sequenced correctly
   - Each task includes unit tests, integration tests, loading states, mobile responsiveness, accessibility requirements

3. **Agentic Implementation** – Tasks are executed by agents, with manual step-by-step review or delegated to background execution

### Key Features

**Specs as Living Artifacts**  
Kiro's specs stay synced with evolving code. Developers can ask Kiro to update specs when code changes, or manually update specs to refresh tasks. This solves the common problem where specs become stale during implementation.

**Agent Hooks**  
Event-driven automations trigger agents to run in the background when files are saved, created, or deleted. Examples:
- Generate or update unit tests on save
- Update documentation automatically
- Validate UI design compliance with Figma mockups
- Optimize code for performance

**Steering Files**  
Project-level configuration files (analogous to CLAUDE.md) that guide agent behavior globally. Teams configure:
- Coding standards and conventions
- Preferred frameworks and patterns
- Organization-specific rules

**Model Selection**  
- Default: Claude Sonnet 4.5 (for reliability and reasoning)
- Auto mode: Blends frontier models for latency and cost optimization with caching

**MCP Integration**  
Native MCP server support for tool connectivity (GitHub, databases, CI/CD, documentation).

**IDE Familiarity**  
Built on Code OSS (open-source VS Code). Developers keep existing VS Code settings and Open VSX plugins while accessing Kiro's spec-driven features.

### Known Limitations

**Spec Overhead at Small Scale**  
Martin Fowler's colleague Birgitta Böckeler observed that Kiro generated 16 acceptance criteria for a simple bug fix — illustrating overhead risk for lightweight tasks. Kiro is best suited for features where upfront spec clarity justifies the planning cost.

**SDD Level**  
Primarily operates at Spec-First level. No documented long-lived spec lifecycle for Spec-Anchored or Spec-as-Source maturity.

**Spec Format Coupling**  
EARS notation and hook triggers are Kiro-specific. Migrating accumulated specs to other tools requires reformatting (see S7.1.2 for switching friction).

**Steering Complexity**  
Project management becomes agent-specific. Steering files encode assumptions about agent reasoning that may not transfer to other IDEs.

### Production Validation

- Used in production drug discovery workflows (AWS case studies), compressing project timelines from months to weeks
- Featured at AWS re:Invent 2025 (sessions DEV314 and DVT209)
- Pricing: Free during preview; paid tiers starting at $20/month announced for post-preview

## GitHub Spec Kit

**Release:** September 2025 (GA)  
**Model:** Open-source CLI toolkit  
**Repository:** https://github.com/github/spec-kit (92,135 stars as of May 2026)  
**License:** MIT

Spec Kit is the most widely adopted spec-first toolkit. It is agent-agnostic, supporting 30+ AI coding agents including Claude Code, Copilot, Cursor, Gemini CLI, Codex, and Windsurf.

### Core Architecture

Spec Kit is a CLI-first toolkit that initializes a `.specify/` directory with spec templates and agent-specific prompts. Developers use slash commands within their agent of choice:

- `/specify` — Define requirements and functional intent (what + why, no tech decisions)
- `/plan` — Define technical architecture, frameworks, libraries, infrastructure (how)
- `/tasks` — Break spec and plan into sequenced implementation tasks

Agents execute tasks step-by-step using these same slash commands, with spec updates flowing through as the implementation evolves.

### Key Features

**Constitution File**  
`.specify/constitution.md` — A project-level "immutable principles" file encoding engineering rules, coding standards, and organizational constraints. Analogous to Kiro's steering files and MyVocaList's CLAUDE.md + rules files.

**Artifact Set**  
Checked into version control:
- `spec.md` — Functional requirements and acceptance criteria
- `plan.md` — Technical decisions, architecture, quickstart
- `tasks/` directory — Implementation checklist
- Optional `constitution.md` — Organizational guardrails

**Agent-Agnostic**  
Slash commands work across 30+ agents without modification. No vendor lock-in to a specific IDE or model.

**CLI Scaffolding**  
`speckit init` sets up `.specify/` templates, constitution, and agent-specific prompts in seconds. Developers can modify templates, add extensions, and create presets.

**Wide Ecosystem Support**  
- GitHub Copilot (Copilot Workspace, Copilot Agent mode)
- Claude Code
- Cursor
- GitHub Copilot CLI (Gemini, Codex, xAI)
- Windsurf

### Known Limitations

**Spec Lifetime Ambiguity**  
Spec Kit creates a new spec branch per change request, suggesting specs are per-feature artifacts rather than long-lived system documentation. The Tessl blog noted this confusion around whether specs are reviewed-once artifacts or maintained living documentation.

**SDD Level**  
Effectively Spec-First. No documented framework for Spec-Anchored lifecycle maintenance or Spec-as-Source enforcement.

**Limited Built-in Automation**  
Unlike Kiro's hooks, Spec Kit does not provide event-driven automations or background task execution. All work is explicit and sequential.

**Community-Driven Maintenance**  
Open source means template quality, extension ecosystem, and update frequency depend on community contribution.

### Adoption & Community

- 90,000+ GitHub stars by September 2025; 92,135 by May 2026 — the most widely adopted spec-first toolkit
- Featured on GitHub Blog and Microsoft Developer Blog
- Integration with GitHub Issues and Copilot Workspace enables spec-to-PR automation

## Tessl

**Release:** Framework (closed beta, September 2025); Spec Registry (open beta, September 2025)  
**Model:** CLI + Registry (freemium)  
**Registry:** https://tessl.io/registry (10,000+ library specs + 3,000+ skills)  
**SDD Philosophy:** Only tool explicitly targeting Spec-Anchored and Spec-as-Source maturity

Tessl is the most ambitious SDD tool. It decouples context (skills, library specs) from code generation, treating agent context as versioned, distributable software with a complete lifecycle: build, evaluate, distribute, optimize.

### Two Core Products

**Tessl Framework (Closed Beta)**  
Guides agents through structured SDD workflows:

1. **Requirement Gathering** – Interactive interview skill that clarifies ambiguous requirements
2. **Spec Writing** – Agents author `.spec.md` files from clarified requirements
3. **Test Linkage** – Specs can link to tests via `[@test]` syntax — tests verify code matches spec intent
4. **Spec Verification** – Automated verification that implementation and tests remain synchronized with specs
5. **Work Review** – Review completed work against approved specs

Specs are stored as long-term memory in a `specs/` directory in the codebase, not discarded per-feature.

**Tessl Spec Registry (Open Beta)**  
A package manager for agent context:

- **Library Context** – Over 10,000 version-matched usage specs for open-source libraries (npm, Maven, PyPI, etc.)
  - Prevents API hallucination by giving agents exact API signatures, examples, and best practices
  - Each spec is version-matched to the library it describes
  
- **Internal Context Packages** – Teams publish internal specs (APIs, conventions, security rules, tech stack guidance) as versioned packages
  
- **Security & Quality Scoring** – Powered by Snyk; evaluations run on every publish before visibility in registry
  
- **Cross-Agent Distribution** – Skills are agent and model-agnostic. Teams install context once via `tessl install` and it works across Claude Code, Cursor, Copilot, Gemini, Codex, Windsurf

### Key Features

**Spec-as-Source Aspiration**  
The most advanced Tessl deployments mark generated code with `// GENERATED FROM SPEC - DO NOT EDIT` and maintain a 1:1 spec-to-file mapping. As of beta, this is file-granular; component-granular spec-as-source is future work.

**Agent-Agnostic Skills**  
Unlike Kiro (IDE-specific) or Spec Kit (agent slash-commands), Tessl's skills are pure markdown that any agent can consume. No framework-specific syntax.

**MCP Server Mode**  
The Tessl CLI doubles as an MCP server. Agents query Tessl for spec context at runtime, enabling dynamic skill discovery and context updates without agent restarts.

**"Vibe-Spec" Mode**  
Tessl supports both human-authored specs and AI-written "vibe specs" — lower-structure workflows for exploratory work that still get checked into the codebase.

**Proof of Effectiveness**  
Internal testing showed teams using Tessl saw **up to 3.3× improvement in correct API usage** across open-source libraries, compared to baseline agent behavior.

### Known Limitations

**Maturity & Availability**  
Framework is closed beta (access by request). Registry is open beta but less mature than Kiro or Spec Kit for core SDD workflows.

**Spec Format Assumptions**  
Tessl's spec format (description, capabilities list, API section, test links) is opinionated. Teams retrofitting existing specs must adjust structure.

**Registry Dependency**  
Tessl strongly encourages publishing and consuming context via the registry. Teams uncomfortable with external dependency or vendor-hosted context may have friction.

**Governance Immaturity**  
While skills are versioned, the process for deprecation, major version policy, and yank procedures is still emerging.

## Comparison Summary

| Dimension | Kiro | Spec Kit | Tessl |
|-----------|------|----------|-------|
| **Distribution** | Proprietary IDE + CLI | Open-source CLI (MIT) | CLI + Registry (freemium) |
| **SDD Maturity Level** | Spec-First | Spec-First | Spec-First → Spec-as-Source (beta) |
| **Agent Support** | Kiro IDE/CLI only | 30+ agents | Claude Code, Cursor, Copilot, Gemini, Codex, Windsurf |
| **Spec Lifetime** | Per-feature | Per-feature branch | Long-lived codebase artifact |
| **Vendor Lock-In Risk** | High (AWS + IDE coupling) | Low (open source, agent-agnostic) | Medium (registry dependency) |
| **Event-Driven Automation** | Hooks (background tasks) | None (explicit sequential) | Skills (manual or MCP-driven) |
| **Constitution/Rules** | Steering files | constitution.md | Distributed skill packages |
| **Library Context** | None built-in | None built-in | 10,000+ versioned specs (registry) |
| **Maturity / GA Status** | GA (July 2025) | GA (September 2025) | Beta (Framework Sept 2025; Registry open beta) |
| **Primary Use Case** | Complex features requiring upfront design | Lightweight to mid-scale spec work | API hallucination prevention + spec-as-source progression |

## Positioning & Adoption Trends

### Kiro
**Best for:** Enterprises prioritizing spec-as-first-artifact, willing to adopt a proprietary IDE. Strong for complex features where design clarity justifies upfront cost. AWS integration and Bedrock backing signal long-term investment.

**Adoption:** Limited but growing; used in production for AWS-aligned teams and drug discovery workflows. Pricing model may accelerate SMB adoption post-preview.

### Spec Kit
**Best for:** Teams already GitHub-native or seeking framework-agnostic SDD. Open-source appeal and 30+ agent support make it the safe choice for multi-tool teams. Lowest barrier to entry.

**Adoption:** Highest — 92,000+ stars, widely referenced in practitioner blogs and vendor guides. GitHub's backing and Copilot integration make it the reference implementation for enterprise SDD.

### Tessl
**Best for:** Teams requiring library-aware agent guidance (prevents API hallucination). Long-term plays on Spec-Anchored and Spec-as-Source maturity. Organizations building internal context packages for multi-team consistency.

**Adoption:** Growing; used by OSS maintainers publishing official library specs. Registry adoption is early but accelerating. 3.3× improvement claims drive interest in data-conscious engineering orgs.

## Architectural Fit for MyVocaList

MyVocaList's current SDD workflow (CLAUDE.md + rules files + specs in `Docs/specs/`) is closest to **Spec Kit's philosophy**:
- Agent-agnostic (Claude Code, future-ready for other tools)
- Spec artifacts checked into source control and maintained long-term
- Constitution-style rules files (CLAUDE.md + rules/*.md)
- Sequential task execution with human review gates

**Tessl Registry integration** would add immediate value:
- Context7 MCP prevents .NET/MAUI API hallucination (already using Context7)
- Tessl's Spec Registry could provide versioned skills for DevExpress, EF Core, MediatR patterns
- Version-matched library specs would reduce task-scope hallucination

**Kiro** would introduce lock-in risk without corresponding benefit at MyVocaList's current scale.
