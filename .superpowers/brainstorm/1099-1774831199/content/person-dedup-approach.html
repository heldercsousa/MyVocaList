Person CRUD — Duplicate Detection Strategy

A person has a FullName (required) + optional BirthdayDayMonth (DD/MM) + optional Email. Two people with the same name but different birthdays are different people. How should the system tell them apart?

The core problem

When the admin types "João Silva" to register a new singer — is this a new person, or one already in the database? The system needs a strategy to detect and surface existing matches before the admin finishes typing.

A

Name-only suggestion list (no mandatory disambiguator)

As the admin types, a live suggestion list appears showing all existing persons whose name matches. Each suggestion shows Name + birthday (if set). Tapping a suggestion loads edit mode for that person. If the admin ignores all suggestions and taps Save, a new person is created — no blocking.

Pros

  • Fastest registration — no mandatory fields beyond name
  • Works even when admin doesn't know birthday
  • Non-blocking — never stops the admin cold

Cons

  • Duplicates can still be created if admin ignores suggestions
  • Birthday only helps after a match is found — not enforced
B

Name suggestion + Birthday required when match found

Same live suggestion list as A. But when the admin's typed name matches an existing person exactly (or very closely), the form requires birthday before saving — to confirm it's a different person. If birthday matches an existing record too, the system blocks save and highlights the existing person.

Pros

  • Strong duplicate prevention when names collide
  • Birthday only required when it matters
  • Clear signal to admin: "we found someone with this name"

Cons

  • Admin may not know the birthday on the spot
  • More complex form state (field appears conditionally)
C

Name suggestion + Birthday always optional, Email always optional

Live suggestions as in A. Birthday and Email are always visible on the form as optional fields — admin can fill them or not. The system uses Name + Birthday as a composite uniqueness check: same name + same birthday = duplicate (blocked). Same name + no birthday = allowed (creates a new record, warns admin).

Pros

  • Full flexibility — admin enriches data when they have it
  • Composite key prevents exact-match duplicates
  • Email is optional differentiator (useful for marketing later)

Cons

  • Two people named "João Silva" with no birthday = two valid records (admin must manage)
  • Form has more fields — slightly heavier for simple cases

💡 The existing Person entity already has BirthdayDayMonth (DD/MM format, optional) and Email (optional). The domain already has GetDisplayIdentifier() that prioritises Email → Birthday → ID for display in suggestions.
