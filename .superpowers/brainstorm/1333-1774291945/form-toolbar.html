VenueFormPage — FloatingToolbar Options

The form has one input field (venue name). Toolbar minimum is 3 slots. Three approaches — pick one or discuss.

A

No FloatingToolbar — keep inline buttons

Save + Cancel as labeled buttons inside the ScrollView, above the keyboard. This is the existing pattern, and it's actually the correct MD3 recommendation for forms with keyboard input. The keyboard pushes content up naturally. FloatingToolbar at the bottom would be hidden behind the soft keyboard on Android — a confirmed conflict per the project's own rules.

B

FloatingToolbar: Save · Cancel · Clear

3-slot toolbar with icon-only buttons. Save (checkmark), Cancel (close), Clear (eraser — resets the name field). Toolbar is positioned above the keyboard using KeyboardAvoidingBehavior or the form's ScrollView handles avoidance. Save button IsSelected=true when form is valid (uses SecondaryContainer highlight).

C

FloatingToolbar in SmallAppBar trailing slots (no bottom toolbar)

Put Save and Cancel as trailing icon buttons in SmallAppBar (Action1 + Action2). Third action could be Clear (Action3). No bottom toolbar at all — the app bar IS the action surface. This is a valid M3 pattern for simple forms: "top app bar provides the form controls."

My recommendation: Option A — keep inline labeled buttons on the form. The project's own dialogs-validation.md rule explicitly says forms with keyboard input use Shell nav pages with SafeAreaEdges="All" + ScrollView — not bottom sheets or bottom toolbars — because of the keyboard conflict. FloatingToolbar at the bottom is architecturally the same problem. Option A is the right call unless there's a strong reason to override that rule.
